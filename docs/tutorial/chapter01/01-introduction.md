# 1.1 ROS 简介

> 本节学习目标：理解 ROS 是什么、解决什么问题、它的设计目标和历史背景，建立对 ROS 的整体认知。

---

## 1.1.1 ROS 概念

**ROS = Robot Operating System（机器人操作系统）**

但严格来说，ROS 并不是一个真正的操作系统。它运行在 Linux（通常是 Ubuntu）之上，是一个**松耦合的分布式通信框架**。

### ROS 的本质

```
┌─────────────────────────────────────────────────────┐
│                    用户的应用程序                   │
├─────────────────────────────────────────────────────┤
│                  ROS（中间件层）                    │
│   ┌──────────┐  ┌──────────┐  ┌────────── ┐         │
│   │ 通信机制 │  │ 开发工具 │  │ 软件生态  │         │
│   │ Topic    │  │ rviz     │  │ 导航     │         │
│   │ Service  │  │ rqt      │  │ SLAM     │         │
│   │ Action   │  │ rosbag   │  │ 感知     │         │
│   │ Parameter│  │ Gazebo   │  │ 控制     │         │
│   └──────────┘  └──────────┘  └──────────┘         │
├────────────────────────────────────────────────────┤
│              Linux (Ubuntu) — 真正的操作系统       │
├────────────────────────────────────────────────────┤
│                   硬件（CPU / GPU / 传感器）        │
└─────────────────────────────────────────────────────┘
```

> 💡 **一句话理解**：ROS 是**机器人应用程序的"胶水层"**，让不同的程序模块能够方便地通信和协作。

### 为什么需要 ROS？

在 ROS 出现之前，开发机器人软件面临以下痛点：

| 痛点 | 描述 |
|------|------|
| **重复造轮子** | 每个团队都自己写一遍驱动、通信、可视化 |
| **紧耦合** | 代码牵一发动全身，换一个传感器要改无数地方 |
| **语言壁垒** | C++ 写的高效模块和 Python 写的 AI 模块难以互通 |
| **调试困难** | 没有统一的数据录制、回放、可视化工具 |
| **单打独斗** | 一个人难以掌握所有领域（感知、规划、控制、驱动） |

ROS 的解决方案：

| ROS 提供的 | 效果 |
|-----------|------|
| **标准化通信接口** | 模块之间通过 Topic / Service / Action 交互，互不依赖 |
| **多语言支持** | C++ / Python / Java / Lisp 等，节点间语言透明 |
| **海量开源生态** | 传感器驱动、SLAM、导航、机械臂控制……拿来即用 |
| **统一工具链** | rviz 可视化、rosbag 录制回放、rqt 调试工具 |
| **分布式部署** | 节点可以运行在不同电脑上，通过网络通信 |

## 1.1.2 ROS 设计目标

ROS 的设计哲学可以概括为三个关键词：

```
┌─────────────────────────────────────────────────┐
│                                                 │
│    🔄 分布式    📦 模块化    🆓 开源             │
│                                                 │
│    · 节点独立运行  · 单一职责   · BSD 协议       │
│    · 松耦合通信    · 可复用     · 免费商用       │
│    · 支持多机      · 可替换     · 社区驱动       │
│                                                 │
└─────────────────────────────────────────────────┘
```

### 核心设计原则

| 原则 | 说明 | 举例 |
|------|------|------|
| **Peer-to-Peer** | 节点之间点对点通信，不经过中心节点中转数据 | Publisher → Subscriber 直连 |
| **分布式** | 节点可以分布在不同的机器上 | 导航在服务器，驱动在机器人 |
| **多语言** | 节点可以用不同语言编写 | C++ 写驱动，Python 写 AI |
| **松耦合** | 节点通过接口交互，内部实现无关 | 换相机驱动，导航代码零修改 |
| **可复用** | 每个节点是独立的模块 | SLAM 节点既可用于小车也可用于无人机 |
| **免费开源** | BSD 协议，可商用 | 工业界广泛使用 |

> 💡 **设计精髓**：ROS 不试图做一个"大而全"的机器人系统，而是提供一个**标准化的协作框架**，让每个人专注于自己擅长的领域。

## 1.1.3 ROS 发展历程

了解历史有助于理解 ROS 的演进逻辑和 ROS 1 vs ROS 2 的区别。

```
2007 ─── 斯坦福大学 STAIR 项目诞生 ROS 雏形
  │
2008 ─── Willow Garage 公司接手，开始正式开发
  │
2010 ─── ROS 1.0 发布（Box Turtle）
  │       首个正式版本，基于 Python
  │
2011 ─── turtlesim 小海龟仿真器发布
  │       成为 ROS 入门的标志性教学工具
  │
2012 ─── ROS 社区爆发式增长
  │       PR2 机器人全面运行 ROS
  │
2013 ─── ROS 全球用户突破 10 万
  │        工业界开始关注
  │
2014 ─── ROS 2 项目启动
  │       为解决 ROS 1 的实时性、多机、安全性缺陷
  │
2017 ─── ROS 2 首个正式版本（Ardent）发布
  │
2018 ─── ROS 1 Melodic 发布（LTS 长期支持）
  │
2020 ─── ROS 1 Noetic 发布（ROS 1 最后一个 LTS）
  │       ROS 2 Galactic 同期发展
  │
2025 ─── ROS 1 Noetic 官方支持结束
  │       ROS 2 成为主流
  ▼
现在 ─── 大量遗留项目仍使用 ROS 1
         新项目推荐 ROS 2
         但 ROS 1 的核心思想完全适用于 ROS 2
```

### ROS 1 版本时间线

| 版本代号 | 发布时间 | 对应 Ubuntu | LTS |
|---------|---------|-------------|:---:|
| Box Turtle | 2010-03 | Ubuntu 10.04 | ❌ |

| Hydro | 2013-09 | Ubuntu 12.04/13.04 | ❌ |

> ⚠️ **本教程使用 ROS 1 Noetic**，运行在 Ubuntu 20.04 上。这是 ROS 1 的最后一个 LTS 版本，也是目前最稳定的 ROS 1 版本。

### 为什么还学 ROS 1？

尽管 ROS 2 是未来趋势，但学习 ROS 1 仍然很有价值：

| 理由 | 说明 |
|------|------|
| **存量项目巨大** | 大量工业机器人、科研项目仍基于 ROS 1 |
| **核心思想一致** | 节点、Topic、Service、Action、Launch 等概念完全通用 |
| **学习曲线平缓** | ROS 1 文档丰富、社区成熟、问题容易找到答案 |
| **迁移成本低** | 学会 ROS 1 后，迁移到 ROS 2 只需适应 DDS 和新的构建系统 |
| **生态完整** | 很多经典功能包（如 move_base、gmapping）在 ROS 1 上最成熟 |

> 💡 **建议**：如果你是 ROS 新手，从 ROS 1 入门可以快速建立信心，之后再迁移到 ROS 2 会非常顺畅。
